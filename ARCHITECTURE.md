# ARCHITECTURE.md — Transit

System design of the Transit geo-telemetry engine: the path a GPS ping takes, the components
it passes through, the spatial model, and the concurrency model.

> **Source discipline.** Every technical claim here is traceable to a `file:line` in this
> repository. Where a prior document and the source disagreed while this file was assembled,
> the source won and the correction is recorded in `AUDIT.md`. Terms in **bold** are defined
> in the glossary at the end.

**What this is:** *Real-time geo-telemetry ingestion and broadcast engine — the
vehicle-location and live-fan-out core of a Fleet-Engine-style backend, at demo scale,
without trip lifecycle management, routing-grade ETAs, or client SDKs.*

## 2. Package layout and the layering rule

```
backend/cmd/server/main.go      Composition root. Wires everything. No business logic.
backend/internal/database/      Repositories. SQL only. No business rules.
backend/internal/services/      Business logic. Depends on repository interfaces.
backend/internal/handlers/      Echo HTTP controllers. Depends on service interfaces ONLY.
backend/internal/hub/           WebSocket hub. Channel-based broadcast.
backend/internal/cache/         Redis client behind an interface.
backend/internal/middleware/    CORS, errors, logging, recovery.
backend/internal/models/        Domain structs. No behavior beyond validation.
backend/internal/config/        Env loading.
backend/pkg/geo/                Pure functions. Haversine, H3 helpers. No I/O, no state.
```

**The layering rule:**

```
handlers → services → repositories → database
```

- A handler **must never** import or call a repository.
- A handler **must** depend on a service interface, not a concrete type.
- A service **must** depend on a repository interface, not a concrete type.
- `backend/pkg/geo` depends on nothing internal. Pure functions only.

Any violation is a bug, not a shortcut. This is the rule DEFECT-1 broke — see `AUDIT.md`.

**Interfaces are declared by the consumer.** `internal/handlers/interfaces.go` declares the
service interfaces handlers need; `internal/services/interfaces.go` declares the repository
interfaces services need. `main.go` holds compile-time assertions (`main.go:30-42`) that each
concrete type still satisfies the interface it is injected as — the one place allowed to
import both an interface's package and its implementation's package.

### 2.1 Why the directory boundaries exist

- **`backend/` vs `frontend/`** — different languages, different toolchains, no shared build
  step, dependency file, or linter.
- **`infra/`** — a different deploy unit. It spans both trees (builds from `../backend/`) and
  belongs to neither.
- **`internal/`** — compiler-enforced, not convention: only `transit-backend/...` code can
  import it. That is what makes packages inside it freely renameable, which the Phase 2 rename
  relied on.
- **`pkg/geo/`** — the deliberate opposite. `distance.go` imports only the standard library's
  `math`; nothing under `pkg/` imports `internal/`. No I/O, no state, no clock reads. That is
  why it is the one package that reaches 100% coverage — pure functions need no fixtures.
- **`backend/migrations/`** — a Go package solely so `//go:embed *.sql` can compile the schema
  into the binary, so the running server carries its own migrations.

## 3. The life of one ping

The write path, device to moving dot. Hops 1–2 happen once per browser tab; 3–15 happen for
every ping.

```
device → POST /api/location → LocationHandler → IngestService
                                                    ├─(a)→ TimescaleDB   (durable)
                                                    ├─(b)→ Redis         (hot state)
                                                    └─(c)→ Hub channel   (live)
                                                             ↓
                          Hub.Run() → per-client channel → WebSocket frame
                                                             ↓
   browser: websocketClient → messageHandler → Zustand store → <DeviceMarkers /> → marker moves
```

![Sequence diagram: one GPS ping from device through handler, service, TimescaleDB, Redis and the Hub, out over the WebSocket to the browser map](docs/diagrams/ping-sequence.drawio.png)

### Part 0 — the standing connection

**Hop 1 — the browser opens a WebSocket.** `useWebSocket()` calls `wsClient.connect()` in a
`useEffect` with an empty dependency array, so it fires once per mount
(`frontend/src/hooks/useWebSocket.ts:13-21`). Note where this lives: the app's only live socket
opens as a side effect of rendering the header status widget
(`components/Header/ConnectionStatus.tsx:11`). Remove that widget from the layout and live
updates stop, with nothing in the map code to say why.

**Hop 2 — the server upgrades and registers.** `upgrader.Upgrade` converts the HTTP request
into a persistent connection (`handlers/websocket.go:30`). `CheckOrigin` returns `true`
unconditionally (`websocket.go:16-18`) — any page anywhere may open this socket, a real gap
outside a local demo. The handler builds a `hub.Client` with an outbound channel buffered to
**256** (`websocket.go:36`), pushes it onto the Hub's `Register` channel, and starts two
goroutines, `WritePump` and `ReadPump` (`websocket.go:41-42`). `Register` is unbuffered
(`hub/hub.go:39`), so that push blocks until `Hub.Run()` picks the client up.

`ReadPump` reads from the socket and discards the result. Its real jobs are noticing that the
connection died and refreshing the read deadline on each keep-alive pong. **This server never
accepts data from a browser over the WebSocket** — traffic is one-directional in practice.

### Part 1 — the ping arrives and is written

**Hop 3 — the device POSTs.** `POST /api/location` with `device_id`, `latitude`, `longitude`,
`speed`, `accuracy`, `timestamp`. Note what is *not* in the body: no `route_id`. The device
does not get to claim which route it is on.

**Hop 4 — the handler validates and nothing else.** Four checks in
`handlers/location.go`: `device_id` non-empty; latitude ∈ [-90, 90] and longitude ∈
[-180, 180]; speed ∈ [0, 350]; and `timestamp == 0` defaults to `time.Now().Unix()`. That is
the whole of the handler's logic. It holds no repository, no cache, and no hub — only an
`IngestService` interface. This is the handler layer doing exactly what the layering intends:
parse, validate, delegate.

**Hop 5 — the service takes over.** `IngestService.IngestLocation` (`services/ingest.go`) owns
all the side effects. Three of its four collaborators are interfaces the `services` package
declares; the fourth reaches directly for the concrete `*hub.Hub` (`ingest.go:21`) — a
layering exception recorded in `AUDIT.md`.

**Hop 6 — branch (a), the durable write.** The only branch whose failure aborts the request.
`LocationRepository.Insert` computes the H3 cell if unset, converts the unix timestamp, and
runs one `INSERT` into `location_history` with seven columns: `time, device_id, latitude,
longitude, speed, accuracy, hex_res9`.

`geom` is **not** in that INSERT. A `BEFORE INSERT` trigger fills it inside Postgres:
`trg_location_geom` calls `update_location_geom()`, which sets
`NEW.geom := ST_SetSRID(ST_MakePoint(NEW.longitude, NEW.latitude), 4326)`
(`migrations/003_add_h3_postgis.sql:97-105,108-118`). The row lands with both a hex ID
(approximate, fast equality) and a PostGIS point (exact, for distance).

**Hop 7 — `route_id` is resolved server-side.** One query against
`database/device_routes.go`:

```sql
SELECT route_id FROM trips
WHERE device_id = $1 AND status = 'IN_PROGRESS'
ORDER BY started_at DESC LIMIT 1
```

A device with no active trip is not an error — `pgx.ErrNoRows` becomes `("", nil)`. This is one
extra round-trip per ping for a value that never changes: nothing in the running server ever
advances a trip, so the answer is static for the demo's lifetime.

**Hop 8 — branch (b), the hot-state write.** The location is assembled into a
`map[string]interface{}`, type-asserted back into a typed struct, JSON-encoded, and written
under key `device:<id>:loc` with a 5-minute TTL (`cache/redis.go:49,56`;
`DeviceLocationTTL` at `cache/interface.go:20`). Failure is logged and execution continues.

Two honest observations: the wired path is a self-declared deprecated compatibility shim, and
the map round-trip is pure overhead (typed struct → map → typed struct). And **nothing reads
this cache back** — the write half of the hot path is built, the read half is not.

**Hop 9 — branch (c), the broadcast.** A `hub.Message` is built and pushed onto the Hub's
`Broadcast` channel inside a `select` with a `default:` arm. The channel is buffered to **256**
(`hub/hub.go:38`). If it is full the message is **dropped** with a `log.Printf` — the ping is
still in the database; only the live update is lost. The source calls this backpressure
handling, not an oversight: a slow hub must never block ingestion.

**Hop 10 — the device gets its 200.** `{"status":"ok","hex_res9":"<cell id>"}`. That value is
available only because `Insert` mutated the struct in place at Hop 6.

### Why the write fans into three branches

| Branch | Store | Optimized for | Failure behavior |
|---|---|---|---|
| (a) `LocationRepository.Insert` | TimescaleDB | Durability and history; compresses after 7 days | **Aborts the request** |
| (b) `DeviceCache.SetDeviceState` | Redis | Latency of a single "where is device X *now*" read | Logged, ignored |
| (c) `hub.Broadcast` | in-process channel | Push — nobody asked; delivered anyway | Dropped if buffer full |

(a) and (b) are the classic split: the durable store is authoritative but slow to answer
"latest per device"; the cache is fast but expendable. Losing Redis loses nothing permanent.
Losing Postgres loses the history. (c) is separate from both because it is not a *store* — a
cache answers when asked; the Hub answers nobody, it pushes.

**Stated plainly:** the read side of (b) does not exist. Redis is written on every ping and
never read. The durability-versus-latency split is the design; only half of it is implemented.

### Part 2 — the broadcast

**What the Hub is.** The single object owning the set of connected clients, built once in
`main()` and run on its own goroutine. Everything else in the backend is per-request; a
broadcast cannot work that way, because the client set is shared, long-lived, and mutated
concurrently. The Hub owns it through three channels and a mutex, so no caller touches
`Clients` directly:

- `Register` — a client joins (unbuffered)
- `Unregister` — a client leaves (unbuffered)
- `Broadcast` — one message for everyone (buffered 256)

One input, N outputs: fan-out.

**Hop 11 — `Hub.Run()` fans out.** Takes a read lock, iterates every registered client, and
attempts a non-blocking send onto each client's own channel. The `default:` arm is a **silent
drop**: a client whose 256-slot buffer is full simply misses the update — nothing logged, no
metric, no disconnect. A stuck client falls permanently behind because its buffer never drains.

Note there are **two drop points on the same path, and they fail differently.** Hop 9 drops for
*everyone* and logs it. Hop 11 drops for one client and records nothing at all.

**Hop 12 — `WritePump` writes the frame.** Sets a 10-second write deadline and calls
`WriteJSON`. The same loop has a second case: a ticker sending a WebSocket keep-alive ping
every `pingPeriod`, which is `(pongWait * 9) / 10` (`hub/client.go:18`) — protocol plumbing to
detect dead connections, with nothing to do with a GPS ping. Constants at `client.go:12-21`:
`writeWait = 10s`, `pongWait = 60s`, `maxMessageSize = 512`.

### Part 3 — the browser moves the dot

**Hop 13** — the `onmessage` callback forwards the raw event to `handleMessage`. There is no
queue, batching, or throttle: one frame in, one synchronous handler call, one store write, one
render pass.

**Hop 14 — parsed and dispatched.** `JSON.parse` inside a `try/catch`, then a `switch` on
`raw.type`. Fields are read through a schema map so wire names live in one file. `speed` is
read with `?? 0` — nullish, so a real `0` survives. A last guard rejects unparseable
coordinates.

`accuracy` is sent by the backend, declared in the frontend schema, and **read by nothing**.

**Hop 15 — the store updates and the marker moves.** The Zustand slice copies the Map and sets
one key. The copy is the point: a **new** Map identity is what tells React something changed —
mutating in place would update the data and render nothing. The marker component subscribes,
re-renders, and because each `<Marker>` is keyed by device id, react-leaflet updates the
existing marker's position rather than destroying and recreating it. That is why the dot
appears to move rather than blink.

## 4. Graceful shutdown and the drain (D28)

`Hub.Run(ctx)` takes a context. On `ctx.Done()` it stops reading `Broadcast` — from that
moment nothing new is forwarded — then snapshots and clears the client set under the lock,
releases the lock, and drains.

**Draining is parallel: one goroutine per client, joined by a `sync.WaitGroup`**
(`hub/hub.go:63-72`). This is not optional. Sequential draining would make shutdown cost
`N × clientDrainTimeout`, so shutdown duration would scale with connection count — itself a
worse defect than the one being fixed.

Per client, `drainAndClose` (`hub/hub.go:131`) polls `len(c.Send) == 0` every
`clientDrainPollInterval` (**1 ms**, `hub.go:24`), bounded by `clientDrainTimeout`
(**250 ms**, `hub.go:19`). A client that has not drained by then has its remainder counted into
`DroppedMessages`, logged, and the channel closed anyway. The hub is the only writer to `Send`
and therefore the only closer.

**Worst-case shutdown is 250 ms regardless of client count**, because the drains run
concurrently. `Shutdown()` blocks on `h.done`, which closes only after `wg.Wait()` returns, so
its return now means "the backlog has been handed to the write pumps."

One honest ceiling: this waits for `WritePump` to *receive* the backlog, not to finish writing
it — the last message may still be inside `Conn.WriteJSON` when it returns. Closing that gap
would need a per-client done signal from `WritePump`; not built.

## 5. The wire envelope

Flat. No `data` wrapper. No `heading`, and none is being added.

```go
type Message struct {
	Type      string  `json:"type"`
	DeviceID  string  `json:"device_id"`
	RouteID   string  `json:"route_id"`
	Latitude  float64 `json:"latitude"`
	Longitude float64 `json:"longitude"`
	Speed     float64 `json:"speed"`
	Accuracy  float64 `json:"accuracy"`
	H3Hex     string  `json:"h3_hex"`
	Timestamp int64   `json:"timestamp"`
}
```

- **No `omitempty` on numeric fields.** A stopped device must serialize `"speed": 0`, not omit
  the key, or the browser cannot distinguish "stopped" from "not reported".
- **`timestamp` is unix seconds (`int64`)**, not RFC3339 — matching what `models.Location`
  already carries, so nothing converts at the point the message is built.
- **DB column and Go model field stay `hex_res9`**; `Message.H3Hex` carries JSON tag `h3_hex`.
  One name internally, one on the wire.
- **The type literal is `"LOCATION_UPDATE"`, uppercase** (`hub/message.go:20`).
- **`route_id` is derived server-side and never accepted on ingest.**

`hub/message_test.go` pins this shape — nine keys, no `data` wrapper, no `heading`, and `speed`
present as `0`. Any change to the envelope requires updating, in the same commit: the Go
struct, the TypeScript type, the serialization test, and this section.

## 7. Spatial model

**Two notions of "nearby", used together.** H3 gives O(1) hex-equality checks; PostGIS gives
exact distance. Hex cells have hard edges and misjudge near-boundary cases, so PostGIS is the
precise fallback.

**H3 resolution 9**, hard-coded at `services/geofencing.go:22` and `database/locations.go:23`.
Edge length ~175 m; the resolution table at `geofencing.go:222` records **174.375** for
resolution 9. `H3_RESOLUTION` is parsed and range-validated but never consumed — see §9.

**Approach detection.** `GeofenceService.isApproaching` (`services/geofence.go:87-88`) takes
the k-ring of radius **3** around the zone — **37 cells, ≈500 m** at resolution 9. If the
device's hex is in that set, `isApproaching = true`.

**Radius-driven k selection.** `FindNearbyDevices` (`services/geofencing.go:135-141`) uses the
H3 k-ring path for radius ≤ 500 m, computing `k := (radiusMeters / 175) + 1` capped at 5, and
falls through to a direct PostGIS query for larger radii.

**ETA.**

```
d = Haversine(device, zone)
v = device.speed
if v < 1.0 km/h  →  v = 20.0        // DefaultSpeed fallback
ETA_minutes = round((d / v) * 60)
```

Constants at `pkg/geo/distance.go:5-9`: `EarthRadiusKm = 6371.0`, `MinSpeedKmh = 1.0`,
`DefaultSpeed = 20.0`.

### 7.1 Known algorithmic limitations

| Assumption | Status |
|---|---|
| Straight-line distance ≈ travel distance | **OPEN — blocked.** Route-projected distance needs a route polyline; `routes` has no geometry column |
| Proximity ⇒ approaching | **OPEN — blocked**, same root cause |
| Instantaneous speed predicts the next few minutes | **Accepted limitation.** Documented, not fixed |
| Stopped ⇒ 20 km/h `DefaultSpeed` | **Accepted limitation.** Documented, not fixed |

The two accepted limitations are POC-appropriate trade-offs. The two blocked ones are
explained in `AUDIT.md` and tracked as D41–D43 in `IDEAS.md`.

## 8. Data model

Five tables, created by `migrations/001_create_tables.sql`, which also enables the TimescaleDB
and PostGIS extensions.

![Entity-relationship diagram](docs/diagrams/er-diagram.drawio.png)

- **`devices`** — `id` (PK), `name`, `status`. The device roster.
- **`routes`** — `id` (PK), `name`, `description`. **No geometry column** — see §7.1.
- **`zones`** (created as `stops`, renamed by `005_rename_stops_zones.sql`) — `id`, `route_id`,
  `name`, `latitude`, `longitude`, `sequence_number`, `geom GEOMETRY(POINT, 4326)`.
- **`location_history`** — a TimescaleDB **hypertable** (`001:43`), partitioned by `time`.
  Columns `time`, `device_id`, `latitude`, `longitude`, `speed`, `accuracy`, `metadata JSONB`,
  plus `hex_res9` added by `003_add_h3_postgis.sql:7` and `geom` populated by trigger.
  Compression on `device_id` after 7 days (`003:87`).
- **`trips`** — `id`, `route_id`, `device_id`, `started_at`, `current_stop`, `status`. Written
  only by the seed migration; nothing in the running server advances a trip.

Spatial indexes are GIST (`002_add_indexes.sql`, `003:32-33,62-63`); SRID 4326 is plain
latitude/longitude — WGS 84, the system GPS itself uses.

**Migrations** are embedded via `//go:embed *.sql` (`migrations/migrations.go`) and tracked in
a `schema_migrations` ledger the server creates at startup, so `main.go` is the single
authority for schema state. Seed data (`004_seed_data.sql`) provides 5 devices, 3 routes,
15 zones, 4 trips, and 11 `location_history` rows.

## 9. Configuration

Most values are declared in `infra/docker-compose.yml` with a default.

**Wired (7 + 1).** `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` reach the pool via
`database.New`; `DB_MAX_CONNS` and `DB_MIN_CONNS` are consumed at `database/db.go:31-32`.
`REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD` at `cache/redis.go`. `SERVER_HOST` / `SERVER_PORT`
build the listen address. `ENV` is wired weakly — parsed and read in a startup `log.Printf`; it
changes no behavior but is not dead.

**Two dead categories, different bugs, different fixes:**

**(a) Read, validated, then ignored — 3.** `REDIS_POOL_SIZE` (pool size hard-coded 50 in
`cache/redis.go`), `H3_RESOLUTION` (hard-coded 9 in two places), `LOG_LEVEL` (logging is bare
`log.Printf`). `H3_RESOLUTION` is the most misleading of the three because it is *validated*,
which reads as evidence that it matters. The fix is wiring —
`NewGeofencingServiceWithResolution` and `NewLocationRepositoryWithResolution` already exist.

**(b) Never parsed at all — 3.** `WS_READ_BUFFER_SIZE`, `WS_WRITE_BUFFER_SIZE`,
`WS_PING_INTERVAL` appear only in `.env.example`, absent from both `Config` and the compose
file. The fix is deciding whether the knob should exist, then either adding it properly or
deleting it.

Adding a config value without wiring it is a bug. Adding one to `.env.example` alone is both.

## 10. Frontend

![Frontend module graph](docs/diagrams/frontend-module-graph.drawio.png)

`src/` groups by role in the data path, not by file type. Data enters through `services/`, is
normalized into `store/`, and is read by `hooks/` and `components/`.

`App.tsx` is a single static layout with no router and no context providers — not just a
single-page app but a single-*screen* one.

**State.** One Zustand store composed of five slices (`store/index.ts:16-20`): `devices`,
`geofenceEvents`, `zones`, `connection`, `ui`. Slices stay independent — no slice reads
another's state directly. Hooks decide *when* data is fetched; slices hold *what* is currently
known. Keeping them apart means a component that only reads state does not trigger a fetch,
and the WebSocket path — which writes into the store with no hook involved — has somewhere to
write to.

**Network.** One shared Axios instance in `services/api/client.ts` centralizes error handling;
every other `services/api/*.ts` calls through it. `services/websocket/` holds the connection as
a singleton with reconnect logic plus the message handler.

**Map.** `react-leaflet` throughout; `MapContainer` is a static shell that reads no store state
— every live layer subscribes for itself.

Frontend conventions: strict TypeScript, no `any`, no non-null assertions without a comment;
map rendering stays in `react-leaflet` components rather than scattered imperative Leaflet
calls; and **no new UI control ships without working logic behind it** — the DEFECT-3 rule.

## 11. Testing shape

- **Handlers** — `httptest` plus a mocked service interface; happy path and at least one
  failure path per endpoint.
- **Services** — mocked repository interfaces; k-ring membership, hex boundaries, and the
  `DefaultSpeed` fallback branch.
- **Hub** — connect, broadcast to N clients, disconnect mid-broadcast, and a slow consumer that
  never reads. The slow-consumer case matters most: it pins the silent-drop `default:` branch.
- **Integration** — `backend/test/integration_test.go`, behind a `//go:build integration` tag so
  the default `go test ./...` loop needs no Docker. It runs testcontainers against the same
  images production uses and applies migrations through the app's real `RunMigrations` rather
  than a container init shortcut, then drives one end-to-end path:
  `POST /api/location` → row in `location_history` → connected WebSocket client receives the
  update, with the Redis write asserted directly.

**No `time.Sleep` in tests.** Use channels, `sync.WaitGroup`, or `context.WithTimeout`. Tests
must not depend on execution order or shared global state.

## 12. Glossary

**Broadcast** — sending one message to every connected client at once. The Hub's `Broadcast`
channel is buffered to 256; every location update goes in one end and is fanned out.

**Channel** — a Go primitive for passing values between goroutines without manual locking. The
Hub has three: `Broadcast` (buffered 256) and `Register`/`Unregister` (unbuffered).

**Clean architecture** — each layer depends only on the layer below it, through an interface.
Here: `handlers → services → repositories → database`. Describes the intent; §2 and `AUDIT.md`
record where it was and was not honored.

**Compression policy** — a TimescaleDB feature that rewrites old hypertable rows into a
compressed columnar format past an age threshold. `location_history` compresses on `device_id`
after 7 days.

**Connection pool** — pre-opened database connections reused instead of opening one per
request. `database/db.go` configures `pgxpool` with `MaxConns`/`MinConns` from config.

**CORS** — the browser rule blocking cross-origin API calls. This backend allows every origin
(`AllowOrigins: ["*"]`) — fine for a local demo, a hazard in production.

**Fan-out** — one input producing many parallel outputs. The Hub reads one message and writes
it to every registered client's channel.

**Geofence** — a virtual boundary around a location, computed rather than sensed. Approximated
here with H3 cells: a device is "approaching" if its hex is within k-ring 3 of the zone's hex.

**GIST index** — a PostgreSQL index type for non-scalar data (geometry, ranges). Both
`zones.geom` and `location_history.geom` have one, so spatial queries need not scan every row.

**Goroutine** — a lightweight, independently-scheduled function execution. The hub's `Run()`
loop and the Echo server each run in one; every connected client adds two more (`ReadPump`,
`WritePump`).

**H3** — Uber's hexagonal hierarchical geospatial index. Divides the earth into hex cells at
multiple resolutions, each with a unique ID. Used here at resolution 9.

**Haversine** — great-circle distance between two lat/lng points on a sphere. The distance term
in every ETA calculation.

**Hot path** — the fast read route, as opposed to the durable one. Here Redis — though see §3,
Hop 8: it is written and never read.

**Hub** — the component owning the set of connected WebSocket clients and fanning broadcasts to
them. One per process, not per request.

**Hypertable** — a TimescaleDB table that looks normal to application code but is internally
partitioned into time-based chunks. `location_history` is the only one.

**Interface assertion** — `var _ SomeInterface = (*ConcreteType)(nil)`, a compile-time check
with no runtime cost. `main.go:30-42` holds eleven.

**k-ring** — the set of hex cells within N rings of a center cell. k-ring 0 is the center;
k-ring 1 adds its 6 neighbors. Approach detection uses radius 3 — 37 cells.

**`omitempty`** — a Go JSON tag option dropping a field when it holds the zero value. The wire
envelope deliberately has **none** on any numeric field; see §5.

**Ping** — two unrelated meanings here. (1) A GPS location report — the subject of §3.
(2) A WebSocket keep-alive frame governed by `pingPeriod`/`pongWait`. Unrelated to GPS data.

**PostGIS** — a PostgreSQL extension adding geometric types and spatial functions to SQL.
SRID 4326 is plain latitude/longitude (WGS 84).

**Repository** — the data-access layer: holds SQL, returns structs, decides nothing.

**Resolution** — how fine-grained the H3 grid is. Resolution 0 covers continents in a handful
of cells; 15 covers roughly a square meter. This project hard-codes 9.

**Service** — the business-logic layer between handlers and repositories: decides *what* to do
and calls repositories to do it.

**Slice** — one focused piece of Zustand state plus its actions. Five compose the store.

**TTL** — how long a cached value survives before expiring. `DeviceLocationTTL` is 5 minutes.

**Upgrader** — the component converting an HTTP request into a WebSocket connection. This one's
`CheckOrigin` always returns `true`.

**WebSocket** — a protocol upgrading one HTTP request into a persistent bidirectional
connection, so the server can push without a new request per message.
